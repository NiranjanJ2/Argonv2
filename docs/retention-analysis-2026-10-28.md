# Why Argon stops helping after the daily brief — October 28, 2026

## The job and the evidence

The product has one customer: its owner. The job is to help him follow through on a daily plan while his energy, naps, and mood change the day. He says Argon fetches the day but is poor at accountability, nudging, and adapting. He suggested that blocking selected distractions until he explains his situation and makes a plan might help, while acknowledging he has not settled on the exact behavior.

I read the current iOS and Python code and queried the live `agentneon` transcript and service journal over SSH, without changing the server. The transcript has 6,610 events from September 14 through October 28 at 12:47 Pacific. It records one device-token prefix across 182 registration events. The local Mac database has only five older events; the live server is the source for the findings below.

## Diagnosis

**Argon is built to deliver an accurate school brief and enforce a fixed evening block. It does not run a useful plan-revision conversation when the owner's state changes.** The daily brief and task board answer “what is due,” but the owner's hard problem is “what can I realistically begin now?” The code and live behavior align on this gap:

1. **Messages are long and ask for attention without reducing work.** The brief prompt requires Argon to name every item due tonight and tomorrow, and the system instruction also demands the full list when asked what is due. There is no concise summary rule for the daily brief. Among 27 outgoing messages from October 18–27, only two explicitly addressed a missed planned start; many others were due-item recaps, teacher-post updates, or calendar reminders. This makes each follow-up another thing to read when the owner already knows he has work. See `argon/runtime.py` (`_brief_instruction`) and `argon/prompts/argon.md` (the after-school brief and evening rules).
2. **It is not allowed to ask the most useful follow-up.** The prompt says not to create a plan, choose priorities, or prescribe a work session. An unprompted message may ask no question. The live transcript contains 480 `guard_blocked` events: 442 spacing/cap refusals, 27 refused questions, and 11 refused claims that nothing was due. These counts include model retries and are not 480 missed user notifications. They show that the agent repeatedly reaches a delivery policy boundary while trying to speak. The policy protects against nagging, but also prevents a concise “what changed?” when a start slips.
3. **The schedule assumes a stable 8 PM evening.** Proactive checks begin at 16:00 and stop outside the fixed window; the planner opens after 15:36 and defaults to 20:00. The phone arms a repeating 90-minute evening block at the chosen or default time. The iOS scheduler says a Monday choice can carry into Tuesday if the app does not wake to re-arm. Calendar events enter the agent's context, but energy and nap state have no equivalent input. See `argon/schedule.py`, `argon/planner.py`, and `ArgonRoutineScheduler.swift`.
4. **Start can feel like a hard commitment rather than a small step.** Tapping anywhere on a task row calls Start; the server immediately sets a task lock of up to four hours, clears any temporary release, and wakes the phone to apply the lock. In the live record, 11 of 32 task-start events were followed by Stop within 60 seconds, all from October 18 onward. For example, on October 20, a Start at 20:06:05 set a lock and the same task was stopped one second later; this repeated several times that minute. On October 19, Argon itself later told the owner that an unblock it had promised was withdrawn when a task started. The logs establish the sequence, not the owner's reason for stopping. See `ArgonTodayView.swift` (`onTapGesture`) and `argon/runtime.py` (`begin_task`).
5. **Plan submission is not a reliable measure of follow-through.** There are 20 `planned` events. Eleven have a later recorded task start on the same day; nine do not. A person may work without pressing Start, and some starts were immediately stopped. The product still saw nine new plans after the October 7 snapshot, so this is not simple one-time abandonment. It is a weak transition from information and intention to supported action.
6. **The AI cannot maintain the useful shape of the board.** It has tools to add and update individual tasks, but no tool to set tonight's focus list or revise today's start time; those live in the four-step planner submission. The prompt also tells the model not to choose priorities or create a plan. Thus the owner must operate the to-do interface to make the board useful, and the AI mostly narrates it. See `argon/runtime.py` (`_register_tools`) and `argon/planner.py` (`apply`).

## Product direction to test

Treat the daily brief as background data; send a short summary only when it changes what the owner needs to do. Let Argon quietly maintain the task board from trusted sources and the owner's corrections, then suggest one realistic next step using the calendar and his stated capacity. If he says “I napped” or “I have 20 minutes,” let the AI revise tonight's focus and start time directly. At the intended start, if there is no active task, the selected distraction block could prompt a return to Argon to make or revise the plan, with a clear way to defer or release it. One context-aware intervention should replace repeated homework recaps. The AI should be useful through the existing board and lock behavior without requiring a chat habit.

Test this with the owner for a week using three observable outcomes: whether he made or revised a realistic plan, whether he began a chosen next step, and whether the intervention felt helpful rather than coercive. Record when a block, nudge, deferral, or release occurs and why, without treating server polling as engagement. The live journal has 39,182 `/v2/state` requests from October 8 onward; most are automatic refreshes.
